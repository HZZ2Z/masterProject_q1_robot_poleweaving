# Design

## Context

参见 [proposal.md](proposal.md)。当前根目录软链接同时承担 Python 包导入、命令别名和共享资源路径入口。课程目录名含连字符，且共享代码仍有 `envs`、`utils`、`expert` 等顶层导入，因此移除链接前必须确定稳定的模块发现机制，并分开处理模块导入、脚本执行和资源定位。

## Goals / Non-Goals

**Goals:**

- 让源码只通过 `courses/` 与 `shared/` 中的规范路径维护。
- 为根目录之外的课程模块导入提供明确、可重复的配置。
- 让文档命令、Docker、测试及自动化脚本无需根目录兼容软链接即可运行。
- 将迁移后的入口和支持方式记录在维护文档中。

**Non-Goals:**

- 重命名课程目录、Python 包名或重构课程算法。
- 改变已有配置、训练产物、运行日志或模型格式。
- 继续支持依赖根目录链接的旧命令和旧导入方式。

## Decisions

1. **通过项目级 Python 包配置暴露规范目录中的模块。** 在仓库元数据中将现有包名映射到 `courses/`、`shared/` 的唯一实现位置，并采用仓库规定的安装/开发环境初始化方式，使导入不依赖工作目录或根链接。相比在多个测试、入口脚本中重复修改 `sys.path`，集中配置更易维护；相比保留链接，它不会让根目录继续承担源码入口。
2. **脚本命令使用规范文件路径。** 文档、Docker 和辅助工具直接调用 `courses/<课程>/...` 或 `shared/...` 下的脚本；脚本内部的资源根目录应通过自身文件位置或明确的项目根路径解析，不能依赖调用者的当前目录。
3. **按依赖类别分批迁移并立即验证。** 先处理共享模块及课程包导入，再更新课程入口、测试、Docker、工具脚本和文档，最后删除 Git 跟踪的根链接。每批检查引用和路径解析，集成阶段运行可用的导入与测试检查。
4. **保留一次性迁移说明，不保留代码兼容层。** 维护文档列出旧根入口与对应规范路径，供用户更新命令；不增加根包装脚本或新的根级别别名，避免兼容入口重新堆积。

## Risks / Trade-offs

- [开发环境未按项目配置初始化时，包导入可能失败] → 在 README 和环境搭建文档中明确初始化步骤，并验证 Docker 与测试入口采用同一配置。
- [有资源路径仍以旧根路径拼接] → 全仓搜索每个软链接名称，并从仓库根和其他工作目录解析资源，修复为基于模块位置的路径。
- [外部用户依赖旧命令或导入] → 提供旧路径到新路径的迁移表；该迁移属于明确的破坏性变更。
- [仓库已有未提交文档改动] → 实施时保留现有工作区改动，只编辑本变更涉及的引用和维护说明。

## Migration Plan

1. 盘点被 Git 跟踪的根目录链接、所有仓库内引用及真实运行入口，记录现状。
2. 添加项目级模块映射和初始化文档，迁移导入、资源定位、脚本调用与容器配置；各批次完成后运行对应路径/导入检查。
3. 更新课程与仓库文档及维护清单，提供旧入口迁移对应关系，并确认文档示例指向规范位置。
4. 删除所有根目录 Git 跟踪软链接，搜索确认无仓库内依赖后运行集成检查及 `git diff --check`。

回滚时可恢复软链接并撤销路径配置改动；若仅有部分外部用户尚未迁移，应发布迁移说明，不增加新的兼容链接。
